# SEOmi desktop PRD

## Produkt i granice

SEOmi jest niezależną, natywną aplikacją Tauri dla macOS i Windows. Nie jest klonem ani klientem zewnętrznego serwisu. Analizuje strony lokalnie, a dane, których nie da się wiarygodnie wyliczyć z dokumentu HTTP, pobiera wyłącznie po świadomie skonfigurowanym połączeniu z dostawcą.

## Główny przepływ

- [x] Pierwszy ekran: wybór istniejącego projektu lub utworzenie nowego.
- [x] Aktywny projekt jest widoczny w nagłówku i pamiętany między uruchomieniami.
- [x] Audyty, historia, zapisane słowa kluczowe i śledzone pozycje są izolowane per projekt.
- [x] Brak wyniku jest jawnym stanem pustym; aplikacja nie tworzy fikcyjnego audytu.
- [x] Dane integracji DataForSEO są przechowywane per projekt w systemowym magazynie poświadczeń, nie w konfiguracji JSON/localStorage.

## Narzędzia lokalne

- [~] Audyt pojedynczego URL: meta, Open Graph, Twitter cards, nagłówki, obrazy, linki, schema, hreflang, favicon, robots/sitemap, bezpieczeństwo i natywny pomiar timingów HTTP (nagłówki, odczyt treści, łączny czas GET i bajty). Metodyka i timestamp są zapisane, a UI nie przedstawia ich jako browser TTFB, Lighthouse ani Core Web Vitals. Pomiar renderowanego DOM, waterfall zasobów i integracja danych CrUX w tym raporcie pozostają otwarte. Werdykt indeksowalności łączy końcowy HTTP, meta robots, `X-Robots-Tag` i canonical; walidacja HTTP celu canonical należy do crawl-workflow i obejmuje tylko cele zebrane w tym samym runie. Lokalny raport dostępności zachowuje regułę, severity, dowód i rekomendację dla strukturalnego `lang`, landmarków `main`, etykiet pól, nazw linków/kontrolek, `alt`, unikalności ID i referencji ARIA; dla pól bez etykiety pokazuje locator DOM i fragment HTML bez `value`. `input[type=hidden]` i tekstowe pola jawnie oznaczone jako honeypot są wyświetlane osobno, wartości nie są utrwalane, a typ/zachowanie formularza pozostają niezmienione. Jeżeli pole jawnie oznaczone jako honeypot używa typu innego niż `text`, audyt dodaje finding z locatorami i zaleca przywrócenie `input[type=text]`; nie modyfikuje DOM ani formularza analizowanej strony. Ręczne testy kontrastu, klawiatury, fokusu i drzewa dostępności pozostają obowiązkowe.
- [~] Opcjonalna analiza frazy głównej: title, meta description, wszystkie poziomy nagłówków, anchory i znormalizowana treść body są liczone lokalnie wraz z fragmentem dowodu. Aby chronić magazyn projektu, tekst przekraczający 200 000 znaków jest jawnie oznaczony jako częściowy.
- [~] Podgląd wyniku organicznego Google w wariancie desktop/mobile z edytorem title/description, dynamicznym przycinaniem szerokością tekstu, breadcrumb URL i opcjonalnym podświetleniem query; szkic metadanych zapisuje się per projekt i URL. To visual preview, Google może przepisać tytuł/opis; podgląd nie przewiduje pozycji ani rzeczywistego wyglądu live SERP.
- [~] Crawl Custom Search: do 10 zapytań CSS albo ograniczonego XPath, każde z typem wyniku Text/HTML/Attribute; wartości z pobranego HTML są zapisywane per strona i run, a zakładka Custom search pokazuje preview, status/błędy i eksport CSV. Ograniczenie zapisu: do 5 wartości × 1 000 znaków na query/URL oraz wspólny budżet 64 000 znaków na run. To analiza source HTML, nie DOM po wykonaniu JavaScriptu; pełne XPath 1.0 i ponowne zapytanie do starego snapshotu bez refetch pozostają otwarte.
- [~] Lokalna walidacja danych strukturalnych: JSON-LD syntax, kształt `@type`/`@graph`, Schema.org context, absolutne Microdata `itemtype`, podstawowy kształt RDFa i ograniczone profile Product/BreadcrumbList/Article są zapisywane przy wykrytej deklaracji i trafiają do problemów audytu. Walidacja JSON-LD ogranicza traversowanie do 2 048 węzłów/64 poziomów, `@type` do 64 elementów na węzeł i wynik do 500 findings; po przekroczeniu raport jawnie oznacza niepełną analizę. To subset reguł, nie pełny Schema.org vocabulary/validator ani gwarancja kwalifikacji do rich results.
- [~] Osobna podzakładka AMP w audycie strony: lokalne wykrycie dokumentu AMP i relacji `amphtml`, kontrola canonical, charset, viewport, AMP runtime/async, boilerplate i budżetu `amp-custom`, z dowodami oraz integracją w problemy/health score. Nie jest to oficjalny walidator AMP i pojedynczy audyt nie odpytuje celu. W crawl-run HTTP status celu zapisuje się tylko wtedy, gdy URL AMP został przetworzony w tym samym runie; pozostałe cele są jawnie niezweryfikowane.
- [x] Crawler witryny z ograniczeniem zasięgu do domeny, limitem stron i ochroną SSRF.
- [~] Eksport raportu projektu (JSON/CSV/PDF): JSON, CSV i PDF dla pojedynczego audytu oraz JSON/CSV/PDF dla zapisanych crawl-runów są dostępne. PDF crawl-run korzysta wyłącznie z zapisanego wyniku, z timestampem, scope i konfiguracją; pełny układ raportu i zakres danych wymagają dalszej weryfikacji E2E na macOS i Windows.
- [~] Crawl-run storage: macOS/Windows zapisuje do plików app-data, a web preview do IndexedDB; poprzednie snapshots z `localStorage` są migrowane. Awaria zapisu historii nie może zamieniać ukończonego crawla w błąd crawla; UI pokazuje osobne ostrzeżenie. Zakres/limity oraz brak E2E na obu systemach opisuje G143.

## Semantyczna mapa treści

- [~] Każdy wynik crawla wylicza osobno bounded topical terms i wewnętrzne linki w obrębie głównej treści. Preferuj semantyczne kontenery `main`, `article`, `[role=main]`, `itemprop=articleBody` i typowe article/content wrappers; pomijaj header, nawigację, footer, aside, elementy ukryte oraz rozpoznane sidebary, breadcrumbs, menu i banery zgód. Gdy brak czytelnego kontenera, fallback odrzuca jawne chrome i oznacza ograniczenie metodologii. Nie zmieniaj zwykłych audytów/raportów linków: ich inwentarz nadal obejmuje linki całej strony.
- [~] Zakładka Visualisations pokazuje content-only semantyczny graf stron z bieżącego snapshotu, leksykalne klastry z jawnym progiem, content-link edges, sieroty i dowody przychodzących linków. Interakcje obejmują wyszukiwanie, filtr klastra/sierot, zaznaczanie, przesuwanie tła, zoom/pan i przeciąganie węzłów. Filtry, pozycje węzłów i transformacja widoku są zapisywane lokalnie per aktywny projekt i crawl-run; nie modyfikują snapshotu crawl.
- [~] Osobny Topical plan zapisuje per projekt encję/EAV, ręczne node'y pillar/cluster/supporting, core/outer, intent, zapytania asserted oraz importowane snapshoty query z DataForSEO i GSC wraz z metrykami, timestampem i kontekstem rynku/property/date window; szczegóły i pozostałe luki opisano w G138. Zachowuje możliwe truncation GSC. Hierarchia może być edytowana przez drag-and-drop lub selektor klawiaturowy; osobny drop target przenosi node do korzenia, a cykle są blokowane. Relacje boczne, lifecycle/termin, fakty ze źródłami i dopasowania do crawlowanych URL-i; niecrawlowane kandydaty pochodzą tylko z wewnętrznych linków treści lub sitemap i są jawnie nieaudytowane; klastry crawla można importować idempotentnie jako dowodowe propozycje. Lokalny semantic audit obejmuje coverage/URL matching, częściowe lexical query coverage, obserwowalność encji, near-duplicates, hipotezy overlapu w temacie oraz zapamiętywaną zakładkę porównującą wybrany snapshot z aktualnym pod kątem URL-i, terminów treści, content-linków, przypisań i obserwacji query. Findings zawierają provenance, dowody, ostrożne sformułowanie i typowany następny krok do ręcznej kontroli; walidacja intent/cannibalization przez SERP/GSC, entity graph i weryfikacja driftu, micro-semantic lint, kontekstowe rekomendacje oraz workflow zmian statusu pozostają otwarte w G139. Per-node brief/draft jest lokalny i ręczny, z deklarowanym query, required entities, snippet target, crawlowanymi celami linków oraz niezweryfikowanymi celami z topical planu, które blokują gotowość do czasu crawla, `locked` facts i exact-match gate; każdy akapit wymaga jawnej klasyfikacji, a akapit faktograficzny URL-a oraz deklaracji redaktora, że źródło wspiera całość. Aplikacja nie pobiera ani nie potwierdza źródła. Sentence-level claim matching, semantyczna kontrola parafraz, quality i anti-filler pozostają otwarte w G140. Pełne GSC/AI/off-page workflows pozostają otwarte w G141–G142. Klastry crawla to heurystyka leksykalna, nie embeddings, intencja, topical authority ani prognoza rankingu. Brak treści po JS jest jawnie częściowy.
- [~] Kolejka analiz masowych CSV z anulowaniem i wznowieniem. Import działa lokalnie, deduplikuje URL-e i zapisuje postęp per projekt; zatrzymanie kończy aktualne żądanie, a worker utrzymujący kolejkę po zamknięciu aplikacji pozostaje wymaganiem docelowym.

## Crawler witryny — wymagania docelowe

Crawler jest osobnym zadaniem w projekcie, a nie ekranem z nieutrwalonym wynikiem. Każdy run zapisuje wersję konfiguracji, punkt rozpoczęcia, czas, status, odkryte URL oraz dowody techniczne. Interfejs pokazuje tylko dane wynikające z ukończonych lub trwających żądań.

Aktualnie aplikacja zapisuje do 50 historycznych wyników crawl-run per projekt wraz z timestampem, URL startowym i snapshotem konfiguracji. Dane te są lokalne; porównanie pól między runami oraz wykres zmian pozostają osobnymi wymaganiami docelowymi.

### Konfiguracja crawl-run

- Scope wybierany przed uruchomieniem: host, subdomeny, folder, zewnętrzne linki, typy zasobów i lista URL z CSV/sitemap.
- Limity: URL, głębokość, równoległość, czas, odpowiedź, redirecty oraz polityka query stringów i canonicalizacji. Aktualnie czas ma twardy limit zapisywany w konfiguracji runu; wynik po przekroczeniu limitu jest oznaczony jako częściowy. Konfigurowalna równoległość pozostaje wymaganiem docelowym.
- Filtry include/exclude, user-agent, własne nagłówki, cookies, uwierzytelnienie i proxy są profilami projektu; sekrety zawsze trafiają do systemowego keychaina.
- Robots, crawl-delay i nofollow są ustawieniami świadomymi. Crawl-run zapisuje status robots.txt, efektywny User-Agent, pasujące Allow/Disallow, sitemap directives i konkretną regułę dla pominiętego URL. Specific agent group, wildcard `*`, końcowa kotwica `$` i Allow przy równym tie-break są obsługiwane; percent-encoding zgodny z RFC, raportowanie wszystkich grup agenta i oddzielny audyt robots.txt bez crawl-run pozostają otwarte.
- URL jest canonicalizowany i deduplikowany przed kolejką. Wszystkie zaplanowane URL są walidowane przeciw SSRF przed żądaniem, a po redirectcie walidacja jest ponawiana.

### Renderowanie i lokalny worker

Domyślnym silnikiem jest natywny crawl HTTP. Dla stron zależnych od JavaScript użytkownik może świadomie uruchomić opcjonalny lokalny worker renderujący. Worker nie jest częścią domyślnej instalacji i nie uruchamia się automatycznie.

- Worker nasłuchuje wyłącznie na loopback, wymaga tokenu przekazanego przez proces desktopowy i ma przypiętą wersję zależności.
- Oba procesy niezależnie walidują URL i blokują SSRF; nie obsługują arbitralnych hooków ani zapisu do ścieżek wskazanych przez stronę.
- Worker dostarcza tylko jawnie oznaczone artefakty: DOM po renderze, konsolę JS, nieudane zasoby, iframe/shadow DOM, screenshot i PDF.
- Health check, cancel/resume, izolacja cookies oraz wyczyszczenie sesji po runie są obowiązkowe. Brak workera ma pokazać stan „renderer lokalny nie jest skonfigurowany”, a nie wynik zastępczy.

### Historia, automatyzacja i eksport

- Kolejka emituje rzeczywisty postęp, wspiera pause/cancel/resume i zapisuje częściowe rekordy.
- Harmonogram per projekt wykonuje run z zapisaną konfiguracją i wysyła wyłącznie lokalne powiadomienia o zakończeniu lub regresji.
- Porównanie runów klasyfikuje added/removed/changed i pokazuje różnicę konkretnych pól. Wykresy są tworzone tylko z faktycznie zapisanych runów.
- CSV, JSON i PDF dołączają timestamp, scope, konfigurację i metodologię; pola CSV są zabezpieczone przed formula injection. PDF crawl-run jest natywnie generowany z zapisanego snapshotu, bez ponownego żądania do witryny.
- Lokalne CLI/API/MCP udostępniają tylko te same zatwierdzone konfiguracje i rekordy projektu, z tą samą walidacją URL oraz bez eksportowania sekretów.
